Use this skill only when the user requests a Dashi workflow involving native Codex projects, chats, schedules, or remote work. Its actions use the Agent's official Codex App tools and the board's model tools. This does not give the Taskboard UI cross-service privileges or observe all desktop chats.

Read the complete target issue and comments before any change. Keep the exact issue ID and latest version. A request to open a draft does not authorize sending, execution, ownership, scheduling, or binding. Keep task status separate from execution; mark done only after explicit user acceptance.

## Projects and local directories

Read the current official `list_projects` and the intended board's runtime. In 0.4.6+, read `taskboard_get_app_project_sync` for its current source version, then call `taskboard_sync_app_projects` only for requested synchronization, with that version, userConfirmed:true, source:official-agent, officialTool:list_projects, schemaVersion:2, the actual returned projects and actual observation time. Do not substitute independent CLI projects or invent host/ID/path fields. A conflict requires a new read and an explicit decision, not an automatic overwrite.

The board persists actual Codex App origin tuples and synchronizes same-ID local names and new projects. Source directories are defaults only: existing manual mappings and explicit board directories win. Remote origins remain separate and never configure a local workspace; ChatGPT projects are skipped. Missing sources do not delete board projects, tasks or bindings. Later fresh official snapshots update the same source records and the visible board polls its own data. This is Agent-fed source synchronization, live:false, not an unattended App subscription; current public CLI project/changed belongs to a different project-ID domain and cannot fill that gap.

On an older connection without these tools, preserve the previously supported explicit create workflow: `taskboard_list_projects`, create only requested missing local projects with actual App projectId/label, and separately configure only the user-chosen path through `taskboard_set_workspace`. Never read private Codex state to recover missing source data.

## Explicit existing-chat association

When the user explicitly requests association, use official `list_threads`/`read_thread` to identify the requested chat. In versions exposing `taskboard_list_conversations` and `taskboard_verify_conversation`, the public CLI can also read a saved real chat ID and cwd from the user's actual configuration. Pass the exact board project and issue ID, so its selected worktree is used. Present actual returned titles verbatim. Anonymous MCP sessions, widget IDs, and chats newly created by a separate test engine cannot identify the user's desktop chat. A separately owned public CLI process reading an existing saved chat is a valid source of saved metadata; its `notLoaded` status is not desktop execution state.

Call `taskboard_bind_conversation` with the issue ID, latest version, `userConfirmed: true`, and only identity fields actually returned by the official source. For `source: "official-agent"`, set `officialTool` to the verifying method. For `source: "persisted-official-app-server"`, pass only the real threadId: the board verifies its saved identity and the issue's selected working directory again before writing. Native project/host/turn fields not supplied by the source stay omitted or null; preserve existing verified and unverified fields with their provenance. Read the issue back. A conflict requires a new read and an explicit decision; do not overwrite another binding. Opening a draft or selecting a candidate does not authorize association. To migrate an existing local binding, use `taskboard_verify_existing_binding` with the current version; verification failure preserves it. To remove one, use `taskboard_unbind_conversation` only when requested.

For an explicitly associated local chat, `taskboard_get_persisted_execution`, `taskboard_list_persisted_turns`, and `taskboard_get_persisted_results` read saved snapshots and real turn/item pages. Read the turn list before selecting a turn ID. Keep the source, observation time, `live:false`, and any returned cursor. Do not claim that a latest summary contains the whole history or automatically set issue status from completed/Stop/Interrupt. `refresh:false` reads the stored snapshot without querying the CLI. Migrated Web bindings use the same saved source; unverified history is retained.

In 0.4.5+, when the user asks to save an observation of an explicitly associated local or remote chat, read its actual metadata and visible assistant result through official `read_thread`, then call `taskboard_record_conversation_observation` with the latest issue version, exact current binding tuple, real observation time and actual returned turn fields. Unknown native fields stay null. `taskboard_get_conversation_observation` reads this saved source; it is `live:false`, not a desktop event stream. Do not include user messages, reasoning, commands or tool output in this assistant-result snapshot. The separate local saved result pages preserve public command/tool text and returned status, exitCode or success; missing values remain null.

## Project summary

Use `taskboard_list_issues` for the exact board project, `taskboard_get_issue` for relevant descriptions/comments, and `taskboard_get_document` for its current document/version. Summarize the real business states, open decisions, blockers, due dates and explicitly recorded results. Missing Hook observations are not evidence of idle, running or success. Return a readable summary in the native chat first. Write it to the project document only when the user requests that write, using `taskboard_save_document` and the version just read while preserving unrelated content. Report conflicts rather than overwriting a newer document. Do not invoke the old AI summary route or read native transcript files.

## Import requested native chat task state

For a metadata-only selection list, do not read chat contents. Official `list_threads` is a bounded cross-app result, not proof that every chat shown in a project's sidebar was enumerated. Missing `projectId` does not disprove sidebar placement, and a matching `cwd` is only a directory clue. Do not infer App membership from it. Public saved metadata discovery uses explicit `modelProviders:[]` across providers. `taskboard_list_conversations` defaults to the selected directory; use explicit `scope:local` when the user requests local discovery across directories, preserving title/archive filters and following `nextCursor`. Report the scope, observation time and remaining cursor. `boardProjectId` (and the legacy root `projectId`) is query context, while each `publicProjectId` belongs to the public CLI source; neither verifies App sidebar membership. Preserve null identity fields and explain unresolved screenshot/list differences instead of inventing IDs or blaming pagination without evidence.

Wait for the user to identify the native chats to inspect, then retrieve their actual IDs and available content through official `list_threads`/`read_thread`. Do not discover scope by guessing that every chat in the same folder concerns this issue. List the real chat-to-issue correspondences and requested changes; only import the changes the user actually asks for. Read each target issue and all comments, retain its current version, and use `taskboard_create_issue` or `taskboard_update_issue` as appropriate. Preserve existing IDs and bindings. Use an actual native result as evidence, never an independent test engine or an old UI activity counter. An assistant's completion claim does not authorize marking a board issue done; explicit user acceptance remains required. Do not send messages to inspected chats unless separately authorized.

## Continue saved board AI history in native chat

Read `taskboard_get_ai_history` for the exact issue and `taskboard_get_ai_history_events` for the selected real stored history ID. Show the relevant saved context and its source to the user, then wait for their specific continuation instruction. Old saved run labels/events are historical snapshots, not current desktop execution. Preserve the stored history; do not launch the old floating AI service, overwrite another native chat, auto-send a prepared draft or bind the new draft. If continuation in an existing native chat is explicitly requested, verify its real official ID and use the supported native opening workflow.

## Requested schedules

A request to create or update a schedule authorizes that schedule only. Read matching existing automation definitions before changing them and prefer updating the real matching schedule. Use official `automation_update` with supported fields and the user's requested timing, project and notification preference. Use a heartbeat for a follow-up attached to a chat; use a standalone cron only for an explicit standalone/per-run project task. Include the board issue identifier and a readable instruction to read its current scope and comments before acting.

Keep the actual returned automation ID as a distinct schedule association, never as threadId. In 0.4.5+, read taskboard_list_automations for the board project and use taskboard_bind_automation with the association version just read (0 for a new association), userConfirmed:true and the actual official-tool identity fields. If identity fields came from the public automation definition after a view returned only a card, record identitySource:public-automation-definition. Do not create or change a schedule merely to establish a board association. Read it back. Older installed versions without these tools may record a user-requested association in a comment.

For an associated heartbeat, taskboard_record_automation_observation accepts only metadata actually returned by official read_thread for its exact attachedThreadId and the real observation time. Preserve the actual saved turn ID, status, Unix-second timestamps and visible assistant result when returned; absent or empty results stay null. This is an attached-thread snapshot, live:false and scheduledRunVerified:false, without a verified scheduler run ID. A schedule's ACTIVE configuration or its chat's saved completed turn is not proof of a triggered run. Cron run identity/results and automatic result writeback remain unconnected. Do not mark completed/done or claim that the board UI directly created or executed the native schedule.

## Requested remote chats and worktrees

Use current official `list_projects`/`list_threads` to obtain the exact host, project and chat IDs. Keep host-specific paths separate from local absolute directories. Never call `taskboard_set_workspace` with a remote path or pretend an identically named local folder is the same remote project.

Create a new user-owned chat only when the user explicitly asks for one; otherwise use available subagent/worktree tooling for delegated implementation as allowed by the task. Official worktree creation must return its real paths and identity; do not synthesize managed worktree/project IDs. Associate only the identity that the installed board schema actually supports. If its chat opener supports only local targets, report that limitation instead of constructing an undocumented remote deep link. Do not install, stop or move a shared native runtime to make the workflow appear supported.

For a requested managed-worktree association in 0.4.5+, read official `list_artifacts` in the chat to which the actual worktree is attached. After the issue explicitly selects that returned worktree directory, call `taskboard_record_managed_worktree` with its current version, userConfirmed:true, exact attachmentType/identityKey/payload, officialTool:list_artifacts and observation time. Omit hostId if absent from the official return. Read back `taskboard_get_managed_worktree`. This saves an artifact association only; it neither creates nor archives a checkout and does not change the issue context or business state. A path or branch alone cannot prove a managed artifact identity.

## Skills and slash candidates

When available, `taskboard_list_skills` uses public `skills/list`; `taskboard_list_agents` reads actual user/project custom agent definitions from public configuration. In 0.4.6+, `/` and `@` can select the same real enabled Skills and reuse their v1 references for insertion, saving and reopening. This `/` subset is a Skill reference, not a native command handler or proof of equality with the desktop picker. General native slash commands and built-in agents still require their own real discovery source; never fabricate them or substitute collaboration modes. Empty actual configuration means no candidates. Keep local @task references working independently.

## Public information and directory discovery

`taskboard_get_native_account`, `taskboard_get_native_usage`, and `taskboard_get_native_models` read the selected public CLI's actual account metadata, limits and model catalog only. They do not change the native model, refresh login tokens or replace the configured board operator. `taskboard_list_native_projects` exposes actual saved CLI project IDs and roots with real pagination. These IDs have not been mapped to desktop App IDs: do not synchronize or overwrite existing projects/bindings by comparing paths. Use official App project tools for requested App identity synchronization; copied public directories may be configured only at the user's explicit request. No source implies no invented account, usage, model or project identity.

## Execution observations and Hook trust

`taskboard_get_execution` reports recorded observations, including an explicit not-connected reason. It does not observe the desktop engine through an independent App Server. Official Hook definitions remain optional and disabled until the user reviews and trusts the exact current definition through the official flow and the receiver is explicitly enabled. “Continue without asking” does not replace Hook trust. Never edit trust files, use bypass, read a transcript/JSONL, or fabricate native progress. Missing observations cannot prove idle or success; Stop/Interrupt cannot prove task acceptance.
